# 桌面训练启动超时修复

用户遇到“PAMOs 训练启动失败 / timed out”。现场旧服务仍可响应，任务处于暂停。旧启动器逐次请求session、完整status和trainer；status含全库计数及历史任务，当次返回10,517,711字节，读取超时仅3秒。读取时的TimeoutError未被捕获，启动重试循环尚未接手就直接显示英文异常。不能由此断言某次具体超时都来自同一请求，但这条启动路径确实不应依赖完整任务状态。

## 改动

- 新增带同一session保护的 `/api/v1/health`，只返回ready、根目录、版本、trainer协议2及强度接口标志，不查询数据库或GPU。
- 启动器使用session+health，验证根目录与协议；JSON读取最多16KiB。旧版/不同根目录/其他端口服务明确报错，不终止别的进程。
- 连接/读取超时、暂时不可用进入45秒有界等待；只有端口确实未占用才隐藏启动服务，慢响应不当作没有服务，不因此反复启动进程。
- 中文错误说明、`.local/trainer-launcher-error.log`保留诊断；不向弹窗泄漏会话令牌。
- 状态计数改用SQL聚合，不反序列化全部候选/模型来计数；同步数据库读取移入线程执行。原status字段和历史任务结构保持兼容。

## 真实恢复记录

用户明确授权仅重启PAMOs。核对8765监听归属本目录、训练已暂停、无工作子进程后保存本地控制状态副本，停止原服务；调用修复后的启动器实际启动新版服务，1.094秒准备就绪。没有删除数据/谱面/模型或重建训练库。

新版health响应114字节，当次约0.016秒；3次实际复用探测分别约0.031/0.406/0.063秒。桌面原有CMD入口已实际调用，启动器正常结束，面板连接新接口并显示可用控件和GPU实测读数。此采样不是所有负载下的响应时间保证。

用户随后在面板保存128并行×1、CPU8、7.2GiB预算，开启自动继续并从原新来源任务继续。观察到实际请求采用这些参数，CPU准备251/325时命中233份缓存、当次可用内存约7.66GiB，按每路约1.74GiB估算实际3路。窗口索引和来源链保留；GPU尚在等待CPU准备，未将此记录当作128窗口CUDA容量/效果验收。

已执行Python AST、diff检查、repository_guard及真实服务启动/复用/页面检查；新增单元测试、超时/冲突故障注入、运行中批量变更恢复、128窗口GPU容量专项 **NOT RUN**，保留现有CI。
